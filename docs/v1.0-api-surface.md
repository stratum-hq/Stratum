# Stratum v1.0 public API surface

Status: PROPOSAL (for PM and user review). Nothing here is frozen.
Date: 2026-07-24
Issue: stratum-hq/Stratum#133 (FR-59)
Scope of this document: design and documentation only. It records what the public
surface IS today, what it SHOULD be at 1.0, the open contract decisions, the
semver policy, and the 0.x to 1.0 migration guide. It does not remove, rename, or
restructure any export. Those are follow-up implementation issues, gated on the
decisions below.

## How to read this

- "Public" at 1.0 means: reachable from a package's documented entrypoint (its
  `exports` map / `main`, i.e. `dist/index.js`), and covered by the stability
  promise in the Semver section. Deep imports (`@stratum-hq/lib/dist/...`) are
  NOT public and are not covered, even where the package layout happens to allow
  them today.
- Each package table marks every exported name as one of:
  - `Stable`: intended public and frozen at 1.0.
  - `Review`: exported today, but its name, shape, or public status is an open
    question for 1.0. Listed with the specific concern.
  - `Internal`: exported today but should not be part of the 1.0 promise.
- Grounding: every claim traces to `packages/*/src/index.ts` and the referenced
  source files at base `origin/epic/130-v1-api` (commit ca3a2d3).

## 1. Package classification

Fourteen packages publish to npm; `demo` and `integration-tests` are
`private: true` and carry no public promise.

Not every published package should reach 1.0 at the same time. The proposed
cohorts:

| Cohort | Packages | Rationale |
|---|---|---|
| 1.0 core contract | `@stratum-hq/core`, `@stratum-hq/lib`, `@stratum-hq/db-adapters`, `@stratum-hq/sdk` | Largest, most-consumed, best-exercised surface. These carry the promise most consumers depend on. Version them to 1.0 together so the core import graph is stable as a unit. |
| 1.0 deployable + tooling | `@stratum-hq/control-plane`, `@stratum-hq/cli`, `@stratum-hq/create`, `@stratum-hq/react`, `@stratum-hq/test-utils` | Real, exercised surfaces, but their "contract" is not only a JS import surface (see per-package notes). 1.0-eligible with the caveats listed below. |
| Hold at 0.x (adapters) | `@stratum-hq/mongodb`, `@stratum-hq/mysql`, `@stratum-hq/hono`, `@stratum-hq/nestjs` | Newer or thin, and NOT gated by the integration suite (see CLAUDE.md section 5.2). Keep at 0.x until each has real database-backed coverage, then promote independently. Promoting a surface we have not integration-tested is the kind of promise 1.0 exists to prevent. |
| Never (as-is) | `@stratum-hq/stratum` | Empty npm name reservation at 0.0.1. Stays 0.0.1 until it becomes a real package by explicit decision. |

Independent per-package versioning already holds (versions differ across the
scope today). 1.0 is a per-package stability promise applied when that package's
surface is frozen, not a synchronized bump of the whole scope.

### 2.5 @stratum-hq/control-plane (0.4.0)

Fastify REST API over the library. This is the most important classification
correction in this document.

`packages/control-plane/src/index.ts` is a SERVER ENTRYPOINT. It calls `main()`
at module load: importing `@stratum-hq/control-plane` runs migrations and starts
listening. It exports nothing, and the package has NO `exports` map (it relies on
`main`). It is a deployable, not a library.

Therefore its 1.0 contract is NOT a JS import surface. Its contract is:

- The HTTP REST API under `/api/v1` (routes in `packages/control-plane/src/routes/`).
- The OpenAPI document (`packages/control-plane/src/openapi.ts`, served at
  `/api/docs`).
- The authentication and authorization model (`X-API-Key` and JWT Bearer;
  scope semantics; default-deny; the admin-route list in
  `middleware/authorize.ts`).
- The environment/config contract (`config.ts`).

Recommendation: document control-plane as a deployable whose stable surface is
HTTP + OpenAPI, tell consumers never to `import` from it, and (follow-up, not
this issue) add an `exports` map so accidental deep imports do not resolve. The
REST API and OpenAPI schema are what 1.0 must promise here.

## 3. Decisions for the user

Each decision is stated as current state, options, recommendation, and the blast
radius of freezing the wrong choice at 1.0. Decisions 2a and 2b are implemented
by #132; 2c by #131; 2d is a pre-freeze correctness fix.

### Decision 3a: API-key scope semantics

Current state. `packages/control-plane/src/middleware/authorize.ts:63` checks
`scopes.includes(requiredScope)`: FLAT membership. Consequences:

- An `["admin"]`-only key FAILS a write route (`["admin"].includes("write")` is
  false).
- A `["write"]`-only key FAILS a GET/read route (`["write"].includes("read")` is
  false).

So scopes today are not a ladder at all; a key authorizes only for the exact
strings it holds. `read`, `write`, `admin` read like a hierarchy but do not
behave like one.

Options.

- A. Hierarchical: `admin` implies `write` implies `read`. Implement as a rank
  comparison (`scopeSatisfies(granted, required)`) in the authorize middleware
  and anywhere scopes are checked.
- B. Documented cumulative membership: keep flat `includes`, and document that a
  key must carry every scope it needs, e.g. an admin key that also writes and
  reads must be minted as `["read", "write", "admin"]`. Explicitly document that
  `admin` does not imply `write`.

Recommendation: A (hierarchical). It matches the universal mental model of
read/write/admin, it matches what the `ADMIN_ROUTES` design already assumes
(admin routes are "more privileged"), and it removes two footguns (admin cannot
write, write cannot read) that will otherwise generate support load forever. It
is a check-time change with NO data migration: a `scopeSatisfies` helper replaces
`includes`.

Blast radius of the wrong freeze. If we freeze flat membership (B) at 1.0 and
later move to hierarchical, that is a widening of access (keys previously denied
become allowed), which cannot ship as a patch or minor; it is a major with a
security note. Freezing hierarchical (A) now is the safe direction: the only
behavior change is that `["admin"]` and `["write"]` keys start satisfying lower
scopes, which is the intended fix. Anyone who deliberately relied on "admin
cannot write" (they should not have, and it is not a documented guarantee) sees a
change; call it out in the migration guide.

Interaction: A composes with 3b. Both land in #132 as one scope-resolution and
scope-check change.

### Decision 3b: validateApiKey scope source

Current state. Two divergent scope sources exist:

- `validateApiKey` (`packages/lib/src/services/api-key-service.ts:114`) returns
  `row.scopes ?? ["read"]`: the `api_keys.scopes` COLUMN only. It never joins
  `roles`.
- `resolveKeyScopes` (`packages/lib/src/services/role-service.ts:138`) does
  `LEFT JOIN roles` and returns `role_scopes ?? scopes ?? ["read"]`: the role
  wins when assigned.

The control-plane auth path (`middleware/auth.ts:42`) calls `validateApiKey`.
So assigning a role to an API key has NO EFFECT on control-plane authorization.
Roles are a silent no-op at the auth boundary. The integration test at
`packages/integration-tests/src/api-key-service.integration.test.ts:299`
documents this divergence as current behavior.

Options.

- A. Single source = role-precedence resolution. Make `validateApiKey` compute
  effective scopes the same way `resolveKeyScopes` does (role scopes override
  column scopes when a role is assigned; else column; else `["read"]`). One
  shared `resolveEffectiveScopes(keyId)` used by both.
- B. Single source = column only. Drop or relegate role-based scope resolution
  for keys; `resolveKeyScopes` becomes column-only too.

Recommendation: A. Roles exist to centralize scope grants; ignoring them at the
one place that matters (authorization) makes the feature a trap. A single
`resolveEffectiveScopes` behind both call sites is the source of truth. #132
implements it.

Blast radius of the wrong freeze. If we freeze the divergence (do nothing) at
1.0, roles remain a no-op at auth, and any operator who "restricts" a key by
assigning a narrow role is WRONG about their security posture: the key still
authorizes on its broad column scopes. We would be blessing a latent
authorization bug. If we unify on role-precedence (A), there is a real behavior
change to flag: a key that has BOTH a role AND column scopes will have its
effective scope set by the role, which can NARROW access for keys whose role is
narrower than their column. That is access-narrowing, gated strictly to
keys-that-have-a-role, and it must be in the migration guide (see 5.3). Keys with
no role are unaffected.

### Decision 3c: canonical error-import surface

Current state. Error classes are defined in `packages/core/src/utils/errors.js`
and exported from `@stratum-hq/core`. On this base branch `@stratum-hq/lib` does
NOT re-export them (`lib/src/index.ts` has no error export). #131 (parallel,
unmerged here) makes `lib` re-export them as runtime values. Friction today: the
README tells consumers to install only `@stratum-hq/lib` + `pg`, yet catching a
typed error (`err instanceof TenantNotFoundError`) requires importing the class,
which currently lives only in core, forcing a direct `@stratum-hq/core`
dependency.

Options.

- A. Bless `@stratum-hq/lib` as the canonical error-import surface for lib
  consumers: lib re-exports the SAME class objects from core (never redefines
  them), core stays the definition site, docs point lib consumers at lib.
- B. Bless `@stratum-hq/core` as the canonical error surface: document that any
  consumer catching typed errors adds `@stratum-hq/core` as a direct dependency.

Recommendation: A, with an invariant. lib re-exports the identical class objects
from core, so `instanceof` works no matter which package the consumer imports
from. Direct core consumers (control-plane, adapters) keep importing from core;
lib consumers import from lib. The one hard rule to freeze: NEVER define a second
copy of an error class; always re-export the core object.

Blast radius of the wrong freeze. The dangerous failure is silent: if a package
ever defines its own `TenantNotFoundError` instead of re-exporting core's, then
`instanceof` across import paths breaks (two distinct class identities), and
consumer error handling silently stops matching. Freezing "re-export the same
object" at 1.0 forecloses that entire class of bug. Getting it right is cheap;
getting it wrong is a quiet, hard-to-debug consumer failure.

### Decision 3d: batchCreateTenants contract

Current state. `batchCreateTenants`
(`packages/lib/src/services/tenant-service.ts:350`) runs all inserts in one
`withTransaction`: all-or-nothing (#213). Return type:
`BatchCreateResult { created: TenantNode[]; errors: Array<{index, slug, error}> }`.

- Success: transaction commits, returns `{ created: all, errors: [] }`.
- Failure: the transaction ROLLS BACK (nothing persists), but the catch block
  (lines 435 to 438) returns `{ created: <the in-memory rows pushed before the
  throw>, errors: [one entry at index = created.length] }`.

The problem: on failure, `created` lists tenants that were rolled back and do NOT
exist in the database. The all-or-nothing SEMANTIC and the partial-success return
SHAPE contradict each other. `errors` can hold at most one entry (the transaction
aborts at the first failure), and `created` is misleading after a rollback.

Options.

- A. Freeze as-is. Document that on failure `created` may list rolled-back
  tenants and callers must treat any non-empty `errors` as "nothing persisted,
  ignore created."
- B. Keep all-or-nothing; on failure return `created: []` with the single error.
  Freeze that honest shape.
- C. Keep all-or-nothing; THROW on failure, drop the `errors` array, return
  `TenantNode[]`.
- D. Make it genuinely partial-success with per-row savepoints. Rejected: it
  contradicts #213 and the advisory-lock tree-integrity model.

Recommendation: confirm all-or-nothing as the 1.0 SEMANTIC (correct: tenant-tree
writes take advisory locks and must be atomic to avoid partial trees), and adopt
B for the SHAPE. On success the return is unchanged; only the failure path stops
returning phantom rows. Do it BEFORE the freeze.

Blast radius of the wrong freeze. Freezing A means every 1.x consumer must know
the "created lies on failure" gotcha forever, and eventually someone reads
`result.created` after a partial failure and acts on tenants that do not exist
(hands out IDs, sends welcome emails, seeds config). That is a correctness bug we
would be endorsing at 1.0. B removes the trap at near-zero cost. Note B is
technically a failure-path behavior change (created goes from non-empty to
empty), so it must land before 1.0, not as a 1.x patch. C is cleaner long-term
but a larger signature change; B is the least invasive honest option.

### Decision 3e (bonus): module format (CJS vs ESM)

Not in the mandated set, but it is a real 1.0 contract question. Under
`module: NodeNext`, format follows each package's `type` field. Today the scope
is split: `core`, `lib`, `db-adapters`, `sdk`, `mongodb`, `mysql`, `cli` are
CommonJS; `hono`, `nestjs`, `react`, `create`, `test-utils` are ESM
(`type: module`). A CommonJS consumer that `require()`s an ESM-only package
(e.g. `@stratum-hq/hono`) hits `ERR_REQUIRE_ESM` on Node before 22.

Recommendation: for 1.0, document the split as the current contract rather than
rushing dual-format publishing. Moving a CJS package to ESM-only, or to
dual-format, is a post-1.0 major per package. Surface it so the freeze is a
conscious choice.

## 4. Semver and stability policy for 1.0

### 4.1 What "1.0 stable" promises

For a package at 1.0 or above:

- No breaking change to its PUBLIC surface without a major bump. Public =
  reachable from the documented entrypoint (`exports` / `main`) and listed as
  `Stable` in section 2. Names marked `Review` or `Internal` are explicitly NOT
  covered until a decision promotes them.
- No deep-import promise. `@stratum-hq/pkg/dist/...` is not public even where the
  layout allows it. Packages that lack an `exports` map (control-plane, cli)
  should gain one so this is enforced, not just asserted.
- For `@stratum-hq/control-plane`, the promise is the HTTP REST API under
  `/api/v1` and the OpenAPI document, not a JS import surface.
- Database migrations are forward-only and additive within a major.
- The environment-variable contract is part of the promise:
  `STRATUM_API_KEY_HMAC_SECRET`, `STRATUM_HKDF_SALT`, the JWT secret, and the
  production enforcement of the latter two.

### 4.2 How breaking changes are handled after 1.0

- Breaking change to a `Stable` name: major bump, a CHANGELOG entry, and a
  migration note. Deprecate first where feasible: mark `@deprecated`, keep for at
  least one minor, then remove in the next major.
- Additive changes (new exports, new optional parameters): minor bump.
- Bug fixes that do not change a documented contract: patch.
- Security fixes that MUST break a contract: ship as a major with a published
  advisory. Where a security fix can be made non-breaking (e.g. a new opt-in
  env var), prefer that and document the opt-in. The 0.6.0/0.7.0 hardening set
  (section 5) is the model: behavior tightened, opt-ins added, advisory
  published.

### 4.3 Which packages are 1.0 vs stay 0.x

Per section 1: core/lib/db-adapters/sdk to 1.0 as the core cohort;
control-plane/cli/create/react/test-utils to 1.0 with the per-package caveats;
mongodb/mysql/hono/nestjs held at 0.x until integration-tested;
`@stratum-hq/stratum` stays 0.0.1. Packages below 1.0 keep 0.x semantics (a minor
may break).

## 5. Migration guide outline: 0.x to 1.0

This is the consumer-facing core of FR-59. Every item is a change a real
consumer can hit. Advisory-level references only; no exploit detail. The fixed
and released hardening advisory GHSA-93wm-g5vg-8j6q is public.

### 5.0 Upgrade checklist (do these first)

- Set `STRATUM_HKDF_SALT` and a real JWT secret. Production hard-fails without
  them (0.3.0 hardening).
- Set `STRATUM_API_KEY_HMAC_SECRET` to move API-key hashing from SHA-256 to
  HMAC-SHA256. Existing keys upgrade transparently on next use; without the
  secret you stay on SHA-256. Not breaking, but do it.
- Ensure your application database role is `NOBYPASSRLS` (the default
  `stratum_app` role is). Run migration `019_rls_policies.sql`.

### 5.1 Authorization is default-deny (0.6.0, GHSA-93wm-g5vg-8j6q)

Control-plane routes without a declared tenant scope now fail closed (403).
Config diff and role administration are subtree-scoped; tenant creation is scoped
to the calling key's subtree. Action: make sure each key's scope and subtree
cover the operations it performs; declare a scope for any custom route you added.

### 5.2 API-key scope semantics (pending Decision 3a)

If hierarchical is adopted: `admin` implies `write` implies `read`. Keys minted
as `["admin"]` or `["write"]` begin satisfying lower-scope routes. If you relied
on "admin cannot write" or "write cannot read" (undocumented, and unsafe to rely
on), that behavior changes. Recommended action regardless: mint keys with the
scopes the caller actually needs.

### 5.3 API-key scope source unified (pending Decision 3b, #132)

If role-precedence is adopted: a key WITH an assigned role now authorizes at the
control plane by the ROLE's scopes (previously the `api_keys.scopes` column was
used and the role was ignored). Action: audit any key that has both a role and
column scopes. The role now wins, which can NARROW a key's effective access. Keys
without a role are unaffected.

### 5.4 Webhook signatures bind a timestamp

Signatures now sign `<timestamp>.<payload>` (HMAC-SHA256), deliveries carry an
`X-Stratum-Timestamp` header alongside `X-Stratum-Signature`, and verification
enforces a freshness window (default 300s, `DEFAULT_WEBHOOK_TOLERANCE_SECONDS`).
If you verify signatures manually, update to: read `X-Stratum-Timestamp`, compute
the HMAC over `timestamp + "." + rawBody`, compare constant-time, and reject
deliveries outside the window. The supported call is
`verifyWebhookSignature({ secret, payload, signature, timestamp })`. For
exactly-once handling, de-duplicate on `X-Stratum-Delivery-ID`.

### 5.5 NestJS guard is JWT-authoritative (0.6.0; context via run(), 0.3.0)

The verified JWT tenant claim is now authoritative. The tenant header is only a
FALLBACK used when no JWT tenant is present and can no longer override a verified
identity (`packages/nestjs/src/stratum.guard.ts`). If you relied on a header to
switch tenants while a JWT was present, use the impersonation path instead
(`X-Impersonate-Tenant` plus your `authorize` callback). Separately, tenant
context is now established with `run()` rather than `enterWith()`, fixing
cross-tenant context leaks under concurrency; no consumer action needed.

### 5.6 RLS opt-in for SHARED_RLS (0.7.0, migration 019, ADR-0001)

`SHARED_RLS` tenants now get real Postgres row-level security with `FORCE`, as a
second isolation layer independent of application `WHERE tenant_id` filters.
Requirements: your application DB role MUST be `NOBYPASSRLS` (a superuser or
`BYPASSRLS` role silently defeats RLS, and `enforceRls` hard-fails in
production). Per-transaction context is set with `SET LOCAL app.current_tenant_id`
via `withTransaction`; if you manage connections yourself, set the context inside
the transaction. Cross-tenant or system operations must go through the audited
`withRlsBypass` helper. Run migration `019_rls_policies.sql`. See
`docs/adr/0001-postgres-rls-defense-in-depth.md`.

### 5.7 Behavior fixes in tenant traversal (0.3.1, 0.6.0)

`getAncestors` now includes the direct parent (a prior bug dropped it, so every
depth-1 tenant returned zero ancestors and deeper tenants lost their nearest
parent). `getDescendants` lists the active-scoped subtree. If you built a
workaround for the old `getAncestors` behavior, remove it.

### 5.8 Isolation-strategy constant rename

`SUPPORTED_ISOLATION_STRATEGIES_V1` is deprecated in favor of
`SUPPORTED_ISOLATION_STRATEGIES`. Import the non-deprecated name once it is
exported from `@stratum-hq/core` (the canonical name is not exported yet; that
fix precedes 1.0). The `_V1` alias will be kept one minor and then removed.

### 5.9 batchCreateTenants is all-or-nothing (pending Decision 3d)

`batchCreateTenants` creates every tenant in one transaction: on any failure,
nothing persists. If you relied on partial creation (some tenants created, others
reported as errors), that no longer happens; wrap per-tenant `createTenant` calls
yourself if you need partial success. If Decision 3d adopts option B, the failure
return is `{ created: [], errors: [<first failure>] }`.

### 5.10 TenantContextLegacy (pending naming decision)

If 1.0 renames or drops `TenantContextLegacy` in favor of `TenantContext`,
consumers importing the legacy type from `@stratum-hq/core` or `@stratum-hq/sdk`
migrate to `TenantContext`. No rename is executed in this issue; this flags the
follow-up.
